# 多卡并行：TP / PP / DP（以及为什么它们吃带宽、拖慢速度）

> 一句话：**多卡不是免费的加速，是"用通信换显存"。** 单卡装不下时才值得；能单卡跑就别多卡。

## 1. 三种切法

| 方式 | 切什么 | 通信发生处 | 通信量级 | 特征 |
|---|---|---|---|---|
| **DP**（数据并行） | 每张卡一个**完整副本**，各跑各的请求 | 几乎无（或梯度同步，训练才有） | — | 吞吐线性扩展，显存不省 |
| **TP**（张量并行） | 把**每层的矩阵**按行/列切开（QKV、FFN 都切） | **每一层**都要把部分结果求和（all-reduce/all-gather） | 大、**频率最高** | 显存省得均匀；**对延迟最敏感** |
| **PP**（流水线并行） | 把**不同的层**放到不同的卡（1–12 层在卡0，13–24 在卡1） | 只在**层边界**传一次激活值 | 小、频率低 | 通信省；但**有流水线气泡**，单请求延迟差 |
| （附）EP（专家并行） | MoE 的**专家**分到不同卡 | 每个 MoE 层做 all-to-all | 取决于路由 | MoE 专属；llama.cpp 基本没有，是 vLLM/SGLang 的地盘 |

## 2. 为什么吃带宽和速度（关键推理，自己推一遍就记住了）

对一层 transformer（hidden = h）：

```
通信量  ~ O(b · s · h)          ← 要传的是"激活值"
计算量  ~ O(b · s · h²)         ← 要算的是矩阵乘
通信/计算比  ~ 1/h              ← 与 b、s 无关！
```

**但这是每层都要付一次的钱**，而且：
- **batch(b) 或 seq(s) 越小 → 通信时间占比越高**（因为通信是固定延迟+小数据量，计算量却随 b·s 缩小）。
- **decode 阶段 b=1、s 每次只 +1** → 这是**最吃亏**的场景；
- **prefill 阶段 b·s 很大** → 通信容易被计算掩盖（尤其训练时）。

所以经验结论（也是 P2 要实测的东西）：
> **TP 在 prefill 上可能划算，在 decode 上最不划算；PP 通信省但延迟差。**

## 3. 两个常见误解

1. **"量化能省通信"** —— ❌。通信传的是**激活值**（f16/bf16/f32），不是量化后的权重。
   量化省的是**权重读取带宽**（decode 的瓶颈），**不省卡间通信**。
2. **"多卡一定更快"** —— ❌。3090/4090 这类消费卡**没有 NVLink**，卡间只能走 PCIe 4.0 x16
   （双向理论 ~32 GB/s，实测 all-reduce 有效带宽远低于此，且要同步等待）。通信 + 同步造成的
   kernel 间隙会直接体现在 nsys 时间线上（这也是我们能"看见"它的地方）。

## 4. llama.cpp 里对应什么

| 参数 | 含义 | 对应上面哪种 |
|---|---|---|
| `--split-mode layer`（默认） | 按**层**切到多卡 | 接近 PP 的通信特征（层边界传激活） |
| `--split-mode row` | 按**行**切权重 | 通信更多，接近 TP 的代价 |
| `-ts / --tensor-split` | 指定各卡分到的比例 | 与上面配合用 |
| 真·张量并行 | upstream 在持续补（例如 fused QKV 的 tensor-split 粒度修复 PR #28965） | TP |
| `-n-cpu-moe` | MoE 专家放 CPU | 不是卡间并行，是"显存换速度" |
| RPC backend | 跨机器按层切分 | 分布式 PP 的雏形，但远不是生产级方案 |

**本项目的位置**：主基线坚持**单卡**（避免引入并行变量）；多卡只在 `docs/roadmap.md` 的 **P2** 里做，
且只做"测量"：NCCL 微基准（all-reduce 带宽/延迟）+ TP/PP/DP 三种方式的延迟-吞吐矩阵 + 通信-计算 overlap。

**effBW 的算法**：`effBW = 每 token 必须读的字节数 × tok/s`
（decode 阶段每个 token 要把权重完整读一遍；KV 按 `2×layers×kv_heads×head_dim×dtype` 累加）。
脚本 `scripts/collect_metrics.py` 的 `model_size_bytes × avg_ts` 是**忽略 KV 的保守下界**。

**待核对的两项**：① 模型实际字节数以 `ls -l models/*.gguf` 或 CSV 的 `model_size_bytes` 为准
（上表按 2.32 GiB 估算）；② KV 每 token 字节数按 Qwen3-4B（36 层 / 8 KV heads / head_dim 128 / q8_0）推算，
以 `server_*.log` 里 llama.cpp 打印的 KV 大小为准。

## 解读（**自己写**，每条标 [实测] / [推测]）

- [实测] prefill 峰值出现在 512（7241 tok/s），128 时偏低（6121）→ 短 prompt 下调度/launch 开销占比高。
- [实测] prefill 从 512 → 4096 只掉 4.7% → 该模型/量化下长 prompt 的代价很小。
- [实测] decode d=0 = 189.1 tok/s，effBW ≈471 GB/s = 峰值的 ~50%（**没跑满带宽**）。
- [推测] decode 没跑满带宽的候选原因：MMVQ 反量化开销 / warp 规约 / L2 命中差 / launch 间隙 → 交给 nsys 验证。
- [推测] d=32768 衰减（69 tok/s）快于纯带宽线（按同效率应 ≈94）→ 长上下文瓶颈不只是带宽，FA kernel 效率在下降。
- [待补]：pp 随长度的拐点、σ 是否随配置变化、与 llama.cpp 官方 benchmark 数字的对比。

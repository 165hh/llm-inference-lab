# 路线图：补齐"本项目学不到的能力"

前置事实（结论来自对上游现状与岗位需求的核对）：本项目（llama.cpp 性能工程）能给你的是
**性能工程方法论 / C++·CUDA 系统调试 / 上游协作标准**；它天然不覆盖：

| 缺口 | 内容 |
|---|---|
| ① | PagedAttention、KV 分页与显存管理（llama.cpp 是连续 KV + slot + defrag） |
| ② | 服务端规模化调度：chunked prefill、跨请求 prefix sharing、多租户、SLO、路由、KV 分层/卸载 |
| ③ | 分布式：多机 TP/PP/EP、NCCL、通信-计算 overlap、MoE 专家并行 |
| ④ | 现代 kernel 写法：TMA/wgmma、CUTLASS、Triton/TileLang + autotuning |
| ⑤ | 压缩/训练侧：GPTQ/AWQ/SmoothQuant 实现、LoRA 体系、并行训练 |
| ⑥ | 生产运维与平台：K8s、监控告警、灰度、容量规划、成本归因、SLA |
| ⑦ | 编译栈：torch.compile / TensorRT-LLM / XLA 级图优化与算子融合 |

---

## 0. 排序规则（先读这一节）

1. **当前项目先到 §10。** 本路线图所有项目都依赖同一套测量纪律，而这套纪律正在本项目里成型。
   硬门：**§8 profiling 有结论之前，不要开新项目**（换项目的成本 > 并行收益）。
2. **§8 决策门（唯一例外）**：若 profiling 结论是"CUDA 主路径找不到可改的点"，
   则把 §10 降级为纯分析报告，**立即启动 P1**（P1 覆盖缺口最多，且能接住"引擎侧"的简历叙事）。
3. 之后按 **P1 →（P2 / P3 / P4 按目标岗位选一个）→ P5 章节 → P6** 推进，**一次只做一个**。
4. 每个项目**另开仓库**，但**共用工具与判据**（见 §7）。不允许出现第二套 TTFT 定义。

## 1. P1：分页 KV + 调度策略消融 + 自写 Triton kernel ★首选

**覆盖缺口**：①②④
**形态**：不是"再写一个 nano-VLLM"，而是**调度策略消融研究**，引擎实现只是手段。

要做（engine）：
- block manager（paged KV）+ 连续批处理 + **chunked prefill** + **block 级 hash 的 prefix cache**；
- Triton 手写 paged attention kernel（`block_tables` 间接寻址）+ 一个 autotune GEMM。

**消融/对比矩阵（这是真正的交付物）**：

| # | 对照 | 期望产出的曲线/数字 |
|---|---|---|
| A1 | 静态批 vs 连续批 | 吞吐 vs 并发曲线（连续批的收益随并发上升） |
| A2 | chunked prefill on/off | TTFT p95 ↔ TPOT 的权衡曲线（长 prompt 下 TTFT 抖动收敛） |
| A3 | prefix cache 命中率 0/50/100% | 命中率 vs 吞吐/首 token 延迟 |
| A4 | **paged vs 连续 KV** | 碎片率、最大并发数、显存占用对比（缺口①的正面回答） |
| A5 | Triton kernel vs torch 原生 | kernel 级 microbench（µs、带宽利用率） |

**交付物（验收标准）**：
- [ ] A1~A5 全部有曲线或表格，原始 jsonl 入库，可一键复现；
- [ ] 一篇对照文档：《llama.cpp 的 slot/连续 KV 为什么表达不了分页——从 A4 的数字说起》；
- [ ] 明确写出适用边界（模型规模、seq 长度、是否 PCIe、GPU 型号）。

**复用现有资产**：`sse_bench.py` 的计时口径直接搬；判据（±2σ、<2%）照抄。
**成本/时长**：单卡 3080Ti/4090，40~80 GPU-h ≈ ¥50~150；3~5 周。
**风险**：Triton 与驱动/CUDA 版本兼容；**先用 0.5B~1.5B 跑通再上 4B**。
**面试可答**：①"PagedAttention 为什么省显存"——用你自己的碎片率数字；②"chunked prefill 为什么牺牲 TTFT"；③"前缀共享的收益边界在哪"。

## 2. P2：双卡分布式实测

**覆盖缺口**：③
**形态**：AutoDL 双卡实例（≈¥2.3~3.4/h），**实测而非看书**。

要做：
1. NCCL 微基准：all-reduce / all-gather 的带宽-延迟曲线（注明 PCIe 域）；
2. TP=2 / PP=2 / DP=2 的小模型推理矩阵，测延迟-吞吐与**通信占比**；
3. **通信-计算 overlap**：naive 串行 vs 把 all-reduce 藏进 GEMM；
4. 横向对比：llama.cpp 的 layer-split / tensor-split vs 手写 TP（复用上一项目的认知）；
5. **外推计算**：把实测通信开销代入，"千亿 MoE 需要多少卡/什么互联才不通信瓶颈"。

**交付物（验收标准）**：
- [ ] NCCL 微基准表 + 三种并行方式的曲线；
- [ ] 一份 scaling 外推（含公式与假设，明确标注是外推不是实测）；
- [ ] 结论必须写"PCIe-only 消费卡域"，不得冒充数据中心结论。

**成本/时长**：¥100~250（双卡 × 40~80h）；2~3 周。
**风险**：双卡实例的卡间拓扑（是否 NVLink）因主机而异 —— 先跑 `nvidia-smi topo -m` 记录，作为实验元数据。
**面试可答**：①"千亿模型怎么扩"（给实测通信占比 + 外推）；②"TP 和 PP 的取舍"（用你自己的延迟-吞吐曲线）；③"通信为什么能藏进计算、什么时候藏不住"。

## 3. P3：量化算法（从零实现 GPTQ/AWQ）

**覆盖缺口**：⑤（算法部分）
**形态**：实现逐层量化 + 精度-速度对照，**最终接回 GGUF 体系**（这是与现有项目的结合点）。

要做：
- GPTQ（或 AWQ）逐层量化实现（校准集 → Hessian/激活统计 → 逐列/逐组量化误差补偿）；
- 消融：group size、act-order、校准集规模；
- 指标：perplexity / 小 eval 集准确率 + **真实推理速度（直接复用 `run_bench.sh`）**。

**交付物（验收标准）**：
- [ ] 精度-速度权衡表（RTN / GPTQ / GGUF K-quant 三方对照）；
- [ ] 文档《GPTQ 与 GGUF K-quant 不是一回事：从算法到 kernel 的差异》；
- [ ] 说明误差来源（哪些层对量化最敏感，用数据说话）。

**成本/时长**：单卡 20~40 GPU-h ≈ ¥30~80；2~3 周。
**面试可答**：①"量化算法你怎么做的"；②"为什么 4bit 还能保持精度"（用层敏感度数据）；③"离线量化算法和推理时反量化 kernel 各自解决什么问题"。

## 4. P4：mini 推理平台（唯一 ≈¥0 GPU 成本）

**覆盖缺口**：⑥
**形态**：本地 Docker / 单机 K8s，后端先接 llama-server（复用），再换 vLLM 对比。

要做：
- 网关：多模型、多副本、路由与重试；队列与背压；
- **按队列深度 / TTFT p95 自动扩缩**；灰度发布；
- Prometheus + Grafana：SLO 看板（TTFT p95、错误率、队列长度、每 token 成本）；
- **故障注入**：副本挂掉、延迟毛刺、慢客户端时的路由行为。

**交付物（验收标准）**：
- [ ] 一条命令起全栈（docker-compose / k8s manifest）；
- [ ] 看板截图 + "给定 SLO 需要几个副本"的容量规划计算（含实测 QPS 曲线）；
- [ ] 故障注入的前后对比（路由是否按预期避开坏副本）。

**成本/时长**：≈¥0（本地或 CPU 实例 ¥0.93/h，若后端用小模型）；2 周。
**面试可答**：①"平台部署你做过什么"；②"怎么定容量和扩缩策略"；③"成本怎么归因到每个请求/租户"。

## 5. P5：编译栈对比（做成章节，不做成项目）

**覆盖缺口**：⑦
**形态**：租 1 天卡，把 TensorRT-LLM / torch.compile 接到**同一 harness**上，与 llama.cpp / vLLM 并到一张表。
**交付物**：一张跨引擎对比表 + 每家的适用边界说明（不追求"谁最快"）。
**成本/时长**：¥20~40；3~5 天。

## 6. P6：训练侧并行（按岗位决定）

**覆盖缺口**：⑤（训练部分）+ ③ 的一部分
**形态**：2 卡 FSDP / ZeRO-1 的小模型 scaling 实验：吞吐 vs 卡数、通信占比、梯度累积的影响。
**交付物**：scaling efficiency 曲线 + 与推理侧通信结论的对照。
**成本/时长**：¥50~100；1~2 周。**目标是推理岗可不做。**

## 7. 共用资产与全局纪律

| 资产 | 出处 | 复用方式 |
|---|---|---|
| TTFT/TPOT 计时口径与实现 | `benchmark/serving/sse_bench.py` | 直接拷贝到新仓库 |
| 原始数据 + 汇总 + A/B 对比的模式 | `scripts/collect_metrics.py` | 拷贝结构（raw jsonl → processed csv → 终汇总） |
| 判据：±2σ、<2% 视为噪声、百分位样本数说明 | `docs/experiments.md` | 照抄，**不允许放宽** |
| 环境/构建记录 | `scripts/record_env.sh`、`results/raw/build_*.json` | 每个新项目第一件事就是跑环境记录 |
| Day-1 体检思路（含 profiler 权限） | `scripts/smoke.sh` | 每个新项目写一份自己的 smoke |

**三条纪律（否则又变成"又一个作业"）**：
1. 每个项目必须有**消融/对比表**；
2. 每个结论必须能追到 `results/raw/` 的具体文件；
3. 负结果照样入库。

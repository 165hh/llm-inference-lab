> **LLM Inference Performance Engineering：基于 llama.cpp 的端到端推理部署、性能分析与优化**

当前 llama.cpp 本身就是 C/C++ LLM inference runtime，支持源码 CUDA 构建，也自带 `llama-bench`、OpenAI-compatible server 和 server benchmark 工具，所以很适合拿来做这条主线。:chatgpt-content-reference{index="0"}

# 一、开始之前，先把项目的“问题”定下来

这一点比装 CUDA 还重要。

你不要定义成：

> 我要把 Qwen 跑快。

太空泛。

我建议你整个项目围绕三个问题：

### 问题 1：一个 LLM 请求到底慢在哪里？

区分：

\[
\text{Prefill}
\]

也就是一次性处理 prompt，

和：

\[
\text{Decode}
\]

也就是一个 token 一个 token 地生成。

你最后应该能说：

> 我的 workload 下，prefill 主要卡在哪里；decode 又主要卡在哪里。

---

### 问题 2：系统参数改变以后，为什么性能会变化？

例如：

```text
量化
context length
batch size
并发数
KV cache
GPU architecture
```

不是只画图。

而是：

\[
\text{参数变化}
\rightarrow
\text{内存/计算行为变化}
\rightarrow
\text{性能变化}
\]

---

### 问题 3：我能不能真正修改源码，让系统变快？

这是整个项目最有价值的一步。

最终至少做一个：

```text
CUDA kernel
CUDA backend
memory
scheduler
runtime
```

层面的真实修改。

然后证明：

\[
\text{microbenchmark improvement}
\]

最终转化成：

\[
\text{end-to-end improvement}
\]

需要：

```text

Git
```

# 六、第二阶段：建立基线

这一步才是项目真正开始。

官方已经有：

```text
llama-bench
```

它支持不同模型、prompt processing、线程、GPU offload，并能输出 CSV/JSON/JSONL/SQL；也支持重复实验。:chatgpt-content-reference{index="4"}

你先固定：

```text
GPU = T4
Model = Qwen3-4B
Quant = Q4_K_M
Context = 4096
```

然后测两种核心 workload。

### Prefill

例如：

```text
Prompt length:
128
512
2048
4096
```

记录：

\[
\text{prompt tokens/s}
\]

### Decode

固定 prompt，例如：

```text
512 input
256 output
```

记录：

\[
\text{generation tokens/s}
\]

每组至少：

```text
warmup
+
5~10 repetitions
```

你之前已经学过 benchmark 的这些纪律，这里正好真正用起来。

# 七、第三阶段：开始服务压测

启动：

```text
llama-server
```

然后不要只自己 curl 一次。

正式测：

\[
TTFT
\]

首 token 时间，

\[
TPOT
\]

后续每 token 时间，

以及：

\[
Throughput
\]

总吞吐。

再记录：

```text
P50
P95
P99
```

并发设置：

```text
1
2
4
8
```

当前 llama.cpp 官方已经带 server benchmark 工具，可以直接对 OpenAI-compatible endpoint 做 workload 测试；官方文档也示例了 continuous batching、parallel slots、batch size 等配置。:chatgpt-content-reference{index="6"}

甚至当前还有专门的 SPEED-Bench client，用于测 throughput 和 latency。:chatgpt-content-reference{index="7"}

不过我建议：

> 官方工具用一套，**你自己再写一个小 Python client**。

因为你自己写一次 SSE 流式响应计时，才能真正理解 TTFT 怎么算。

# 八、第四阶段：Profiling —— 项目的分水岭

到这里之前，你都还只是一个比较认真的用户。

从这里开始，才进入 Infra。

目标不是：

> “GPU utilization 90%。”

而是找出：

\[
\boxed{\text{时间到底花在哪几个 kernel 上}}
\]

先把 workload 分开：

```text
Prefill
Decode
```

然后用 profiler 看：

```text
kernel duration
memory bandwidth
register usage
occupancy
shared memory
warp stall
kernel launch
```

最后得到类似：

```text
Prefill:
  MMQ       46%
  Attention 31%
  Others    23%

Decode:
  MMVQ      37%
  Attention 28%
  Others    35%
```

数字这里只是示意。

你的第一个真正高价值成果是：

> **找到一个 hot path。**

# 十、第六阶段：真正改源码

**整个项目能不能超过 nano-vLLM，主要看这里。**

这时才允许你选：

```text
CUDA kernel
backend
memory
scheduler
```

中的一个问题。

不是先决定：

> “我要优化 FlashAttention。”

而是：

```text
profiling
↓
发现热点
↓
阅读对应源码
↓
提出 hypothesis
↓

```

例如：

> 为什么这个 kernel occupancy 低？

或者：

> 为什么 Turing 走了这个配置？

或者：

> 某种 tile size 是否导致 register pressure？

然后：

```text
修改
↓
compute-sanitizer
↓
unit/backend tests
↓
microbenchmark
↓
end-to-end benchmark
```

最后必须回答：

\[
\text{kernel 快多少？}
\]

和：

\[
\text{整个服务快多少？}
\]
